# 提案：「预警到手机」主动推送系统（v5.0 头号功能）

> 给开发者的完整构想书。读完本文你就能开工：目标、架构、数据模型、接口、里程碑、验收标准都在这里。
> 项目底线（务必遵守）：**全免费层、零审批、不收集个人信息、文案口语化、农学参数有出处**（见 AGENTS.md）。

---

## 一、为什么做它（背景与价值）

现在是"人找信息"：桃农不主动打开网页，就看不到霜冻预警。而倒春寒往往发生在夜里——**等第二天看到，花已经冻完了**。本项目解决的就是这个原始痛点，但只完成了一半：我们把预警算出来了，还没送到人手里。

把产品从「拉」变成「推」，是这个项目价值最大的一次跃迁：

- 🌡️ 寒潮来临前 12 小时，村委会/合作社的**微信群**自动收到：「明晨大华山最低 −3℃，低于盛花期冻害临界（−2.8℃），请今晚熏烟+灌水」
- 🐛 梨小食心虫防治窗口开启当天，订阅的农户收到打药提醒
- 💧 连旱 10 天触发浇水提醒

## 二、用户故事

| 谁 | 故事 |
|---|---|
| 桃农老李（不在群里） | 在网页选好村子，点「订阅预警」，选择 ntfy/Bark 通道，寒潮前夜手机弹通知 |
| 村合作社王姐（管微信群） | 把群机器人的 webhook URL 交给维护者（或自助填入），全村自动收预警 |
| 科技小院小王 | 后台调整订阅规则与阈值，核查推送日志有没有漏发/误发 |

## 三、推送渠道（按优先级）

| 优先级 | 渠道 | 成本/门槛 | 适用 |
|---|---|---|---|
| 1 | **企业微信群机器人 webhook** | 零成本、零审批（群→添加机器人→复制 key） | 村委会/合作社群，一次覆盖全村 |
| 2 | **ntfy.sh**（Android/任意） | 免费开源，订阅一个主题名即可 | 个体农户 |
| 3 | **Bark**（iOS） | 免费，类似 ntfy | 个体农户 |
| 4 | 邮件（Resend 免费层） | 需注册 | 备用 |
| 远期 | 微信公众号模板消息 | 需企业资质审批 | 暂不做 |

## 四、架构（延续零后端成本传统，全部免费层）

```
Cloudflare Cron Worker（每小时）
  → 拉有订阅产区的 Open-Meteo 预报（多坐标一次请求，见 §八）
  → 跑规则引擎（复用 index.html 的判定逻辑，抽出为共享纯函数）
  → 对每条订阅：级别过滤 → event_key 去重 → 发送
  → 写推送日志
Cloudflare D1（免费 SQLite）：订阅表 + 推送日志表
Pages Functions（现有 functions/）：订阅管理接口
```

**关键技术准备（也是还债）**：`index.html` 里的霜冻判定/推进方案规则目前内嵌在渲染函数里。第一步要把「纯计算」抽成无 DOM 依赖的 `rules.js`（输入区域数据，输出事件数组），网页端和 Worker 端共用同一套规则——**一份逻辑，两处运行，永不打架**。

## 五、数据模型（D1）

```sql
CREATE TABLE subscriptions (
  id INTEGER PRIMARY KEY,
  region_idx INTEGER NOT NULL,            -- 对应 index.html LOCATIONS 下标
  channel TEXT NOT NULL,                   -- wechat_group | ntfy | bark | email
  target TEXT NOT NULL,                    -- webhook URL / 主题名 / 邮箱
  min_level TEXT DEFAULT 'red',            -- red | yellow（yellow=全部提醒）
  kinds TEXT DEFAULT 'frost',              -- 逗号分隔：frost,pest,water
  active INTEGER DEFAULT 1,
  created_at TEXT DEFAULT (datetime('now'))
);
CREATE TABLE push_log (
  id INTEGER PRIMARY KEY,
  sub_id INTEGER NOT NULL,
  event_key TEXT NOT NULL,                 -- 去重键：日期+种类+产区，如 2026-04-10:frost:1
  sent_at TEXT DEFAULT (datetime('now'))
);
```

## 六、防扰与防误报（决定用户会不会关掉你）

1. **同事件只推一次**：同一 `event_key` 7 天内不重复（冷锋持续多日只报第一声，解除后可推一条"解除"）
2. **双时次确认**：连续两个模式时次（约 1 小时）都满足才触发，砍掉一半误报
3. **级别门槛**：默认只推红色（≤T90 级）；用户可选"黄色也推"
4. **提前量**：霜冻事件在**预计低温夜的前一天 18:00 前后**推（留出备柴/灌水时间）
5. **每周摘要**：即使无预警，每周一条简短摘要，让用户知道系统活着
6. **文案铁律**：每条推送 = 产区 + 日期 + 关键数字 + 一句动作 + "以官方预报为准"

## 七、接口与网页端

- `POST /api/subscribe`：`{region_idx, channel, target, min_level, kinds}` → 写订阅
- `POST /api/unsubscribe`：`{id, token}`（订阅时返回退订 token）
- `GET /api/subscriptions/health`：Worker 自己用，检查 webhook 有效性
- 网页端新增卡片「🔔 预警到手机」：产区已选好 → 选通道（ntfy 主题名/Bark key/邮箱）→ 一键订阅；微信群机器人提供图文教程 + 管理员入口
- 订阅数据纳入「我的记录」导出（target 属敏感信息可选择性导出，默认不含）

## 八、成本与限额核算（全部免费层）

- Workers Cron：每小时 1 次 × 每天 24 次；有订阅产区合并请求（Open-Meteo 支持**逗号分隔多坐标一次拉取**，16 个产区 1–2 个请求搞定）→ 每天约 30–50 次外部请求，远低于免费额度
- D1 免费 5GB：订阅+日志数据量可忽略
- 企业微信群机器人限 20 条/分钟/群：按村粒度天然够用
- **结论：¥0/月**

## 九、里程碑（建议 2–3 周）

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| M1（~1 周） | 规则抽纯函数 `rules.js`（网页端回归通过）+ D1 建表 + Worker cron 骨架 | 网页功能零回归；`wrangler d1 execute` 手动触发能打日志 |
| M2（~1 周） | 企业微信群机器人通道 + event_key 去重 + 双时次确认 | 测试群真实收到预警卡片；重放同一事件只推一次 |
| M3（3–4 天） | 网页订阅 UI + ntfy/Bark 通道 + 退订 + 文档 | 手机端全流程自助完成订阅与退订 |

## 十、验收标准（逐条可测）

- [ ] **回放测试**：用 2026-04 平谷历史数据回放，能在大风降温日前 ~12h 产出霜冻推送记录
- [ ] **去重**：同一事件重放 7 次，`push_log` 仅 1 条；第 8 天后可再触发
- [ ] **真机**：企业微信群实际收到中文预警（产区/日期/低温值/动作建议齐全）
- [ ] **防误报**：单时次临时满足不触发
- [ ] **零回归**：网页端所有现有模块行为不变（rules 抽取后跑 TASKS.md 全局自测）
- [ ] **隐私**：库里只有 webhook URL/主题名/邮箱，无姓名手机号；每个 target 可自助退订
- [ ] **成本**：Cloudflare 账单页面 ¥0

## 十一、风险与对策

| 风险 | 对策 |
|---|---|
| 模式温度偏差（1–2℃） | 文案永远带"以官方预报为准"；临界值取谨慎口径（现状已如此） |
| Open-Meteo 限流 | 多坐标合并请求 + 1h 缓存；失败退避 |
| 微信群机器人 key 泄露 | key 只存 D1；网页端不回显全量；支持一键更换 |
| 用户被扰关通知 | §六的防扰设计 + 退订必须一步到位 |

## 十二、你需要提前准备的

1. Cloudflare 账号权限（D1 + Workers 开启；免费计划即可）
2. 一个企业微信群 + 群机器人（5 分钟：群设置→群机器人→添加→复制 webhook）
3. 手机装 ntfy 或 Bark 做真机测试
